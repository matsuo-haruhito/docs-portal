# 自動リトライ安全性棚卸し

この文書は import / build / mail / webhook の自動リトライを判断するための現行仕様です。処理ごとに、二重実行で起きる副作用、所有権fence、上限、maintenance停止、手動導線を分けて扱います。Docusaurus preview buildは生成ファイルbuildと同じretry policyではなく、`DocumentVersion` 固有の状態機械とartifact整合性によって自動収束します。

## 目的

自動リトライは「失敗した処理をもう一度流せるか」だけでなく、二重実行で外部副作用や通知重複が起きても安全かを確認してから対象ごとに判断します。

この repo では、まず次を分けます。

- 手動再実行で十分な処理
- 自動リトライしても副作用が小さい処理
- retry 前に locking / idempotency key / unique constraint / external id が必要な処理
- 自動化より先に通知や失敗理由の見え方を整える処理

## 共通判定基準

| 判定 | 使う場面 | 先に必要な guard |
| --- | --- | --- |
| 手動再実行優先 | 失敗原因の確認や対象の絞り込みが必要な処理 | runbook、status filter、失敗理由、対象件数の確認 |
| 条件付きで自動リトライ可 | 同じ入力を再処理しても最終状態が同じになる処理 | concurrency key、入力の正規化、retry 親子 metadata、上限回数 |
| guard 追加後に再評価 | 外部送信、通知、永続ファイル更新など二重副作用があり得る処理 | idempotency key、unique constraint、外部ID、dedupe window、locking |
| 通知・可観測性を先行 | まだ delivery 仕様や失敗傾向が見えていない処理 | alert、failure count、失敗 payload の安全な要約、runbook 導線 |

| --- | --- | --- | --- | --- | --- |
| import | `PublishJob` の `pending` / `imported` / `published` / `failed`、`log_message`、manifest の `source_repo` / `source_branch` / `source_commit_hash` | 同じ artifact を再 import したときの `latest_version` 上書き、添付ファイル差し替え、生成ファイル event の再発行 | `DocumentImporter` は import root 配下の path 検証、version label 重複拒否、失敗時の `PublishJob.failed` 記録を持つ | 自動リトライは保留。まず失敗原因と manifest / artifact の同一性を見て手動再実行する | import 対象を 1 種に絞り、source commit hash と version label を使った idempotency / replay 方針を決める issue |
| Docusaurus preview build | `DocumentVersion.preview_build_status`、試行回数、次回試行時刻、claim token、artifact marker、entry HTML、定期run履歴 | 同じ版の重複build、古いworkerによる成果物上書き、停止後のDBとfilesystemの不一致 | 版ごとのDB lockとclaim tokenでcurrent ownerだけがinstall・成功・失敗を確定する。staging後にmarkerを書いて版専用directoryへ置換し、reconciliationが未要求・stale queue/running・backoff経過・artifact不整合を最大5回で収束する。preview recurring runだけは30分staleかつcurrent schedule ownerなら回収できる | 自動収束する。広域`JOB_RELIABILITY_V2_ENABLED`から独立し、`READ_ONLY_MAINTENANCE`中はschedule dispatch、stale回収、reconciliation、build変更処理を停止する。`preview_abandoned`は自動解除しない | 上限到達版を原因確認後に1件だけreset/retryする監査付き管理導線が必要になった場合は別issue |

## 生成ファイルイベント dispatch の所有権契約

buffer event の dispatch は、同じ event 集合を 1 group として claim し、`dispatch_group_id`、推測不能な `dispatch_claim_token`、claim / heartbeat 時刻を全行に保存します。claimは業務metadataへ混ぜず、opaqueな `dispatch_claim` として後続処理へ伝播します。claim付きevent経路は後続jobを別queueへ切り離さず、generator / writerが完了するまでdispatcherのlease内でinline実行します。

stale group の回収では event をばらして `pending` に戻しません。同じ event ID 集合と group ID を維持したまま token を rotate して新しい owner へ引き継ぎます。worker は provider / writer 呼び出しの前後で heartbeat を更新し、完了・失敗確定時には group 全行を lock して、event ID 集合、group ID、token、`processing` 状態がすべて一致する場合だけ状態を変更します。管理画面からの明示的な再投入だけは既存 claim 情報をすべて消し、新しい dispatch group として扱います。

副作用の確定にも同じownership fenceを使います。filesystem writerは一時領域へstageしてからownership lock内で最終pathへpromotionし、DocumentVersion writerはownership確認とDB mutationを同じtransactionに入れます。staged commitを持たないcommand writerはclaim付きevent経路でfail closedとします。旧ownerが後着した場合はevent状態だけでなくfilesystem / DocumentVersionもcommitせず、claim付き失敗は通常の`AutoRetryPolicy`へ流しません。

この契約は同じgroupの再計算を許すat-least-once処理ですが、最終commitをcurrent tokenのownerだけに限定します。外部commandのexactly-onceは保証できないため、claim付き経路では実行自体を許可しません。また、`dispatch_group_id`がないlegacy `processing` eventは完了済みchildとの区別ができないため通常回収では自動採用せず、旧worker / queueのdrainと副作用確認後の手動ackまたは明示的な再投入に限定します。

## 自動リトライ issue に切る前のチェックリスト

- retry 対象は 1 処理または 1 delivery 種別に絞れている
- 同じ入力を 2 回処理したときの最終状態が説明できる
- 外部送信がある場合、相手側で dedupe できる id がある
- status / run / event / log から、手動確認すべき失敗と機械的に戻せる失敗を分けられる
- retry 回数、対象 status、対象期間、bulk 対象件数の上限がある
- 失敗 payload や metadata に機密情報を過剰に出さない
- Webhook delivery を対象にする場合、手動再送、表示範囲まとめて再送、継続失敗 handoff JSON、自動 retry queue の役割差を説明できる
- 既存の `定義を同期`、`即時実行を要求`、event 再dispatch、run 再実行の導線と競合しない

## 現時点の結論

- import は manifest / artifact の同一性と `latest_version` 影響を先に固定するまで、手動再実行を優先する
- Docusaurus preview buildは、`DocumentVersion`の状態、版単位claim token、artifact marker、entry HTMLを正本に最大5回で自動収束する。広域`JOB_RELIABILITY_V2_ENABLED`には結合せず、preview recurring runだけは30分staleかつcurrent schedule ownerの場合に回収する。`READ_ONLY_MAINTENANCE`中は新規dispatchと回収を停止し、`preview_abandoned`は自動解除しない
- generated file buildの自動retryは、`ai_usecase_decision_flow` + `filesystem` writer の failed parent runだけを対象にする。`document_version` writer、import、mail、webhook、手動 retry / bulk retry child run は対象外のままにする
- auto retry metadata は `retry_requested_by_user_id: nil`、`auto_retry: true`、`retry_reason` で手動 retry / bulk retry と読み分ける。parent run 1 件につき auto retry child は 1 回までとし、手動 / bulk retry child の存在だけでは auto retry 済みとは扱わない
- mail は delivery 仕様と外部 idempotency が未確定なため、自動リトライではなく通知・delivery 契約の issue を先に切る
- webhook は HTTP 5xx / response 未取得の failed delivery に限り、token付きclaimで最大3回まで自動再送する。claim時には回数を消費せず、確定したattemptだけ `retry_count` を増やし、stale claimはcount非消費で回収する
- 同じdeliveryの自動再送は `X-Docs-Portal-Delivery` を維持する。POST後・結果確定前停止では重複送信があり得るため、受信側dedupeを前提とするat-least-onceであり、sender単独のexactly-onceではない
- 手動再送は元deliveryを保持して新しいdeliveryを作る。継続失敗handoff JSONは自動再送とは独立したread-only evidenceで、通知・ack・再送を実行しない
- `READ_ONLY_MAINTENANCE` 中はWebhook自動再送のclaim、stale claim回収、HTTP POSTを停止する。指数backoff、上限到達通知、mail自動再送は未実装のまま別issueとする
