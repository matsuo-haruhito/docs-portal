# issue整理

GitHub Issue の内容を読み解き、ユーザーとの対話で仕様を確定させ、`docs/` と Issue を「実装に着手できる状態」にする。

## ゴール

このスキルの完了時、以下が揃っている:

- 該当する `docs/` の仕様文書に要件が反映されている
- 必要に応じて設計判断が文書化されている
- Issue に決定事項がコメントとして残っている

## ワークフロー

### 1. Issue の読解

- `gh issue view <number>` で Issue の内容を読む
- Issue に書かれた課題・要望・バグの本質を理解する
- 該当する仕様領域を特定する（import / viewer / admin / external連携 / infrastructure 等）

### 2. 既存の設計・要件を確認

- `docs/README.md` を入口に、関連する仕様文書・runbook を読む
- `docs/アプリケーション仕様.md` で全体の位置づけを確認する
- 関連するコードを読み、現状の実装を把握する

### 3. ユーザーとの対話で仕様を詰める

以下の観点で不明点・曖昧な点を洗い出し、ユーザーに確認する:

- **スコープ**: この Issue で何を解決し、何は対象外か
- **影響範囲**: 他の画面・機能への波及
- **エッジケース**: 0件、null、上限値、同時操作の扱い
- **表示・UX**: ラベル、文言、画面遷移、操作フロー
- **データ**: テーブル変更の要否、既存データへの影響、マイグレーション方針
- **権限**: internal / external / company_master_admin のどれが対象か
- **優先度**: 段階的リリースの場合、最小スコープはどこか

対話が不要な（Issue の記述で十分明確な）場合はスキップしてよい。

### 4. docs/ の更新

仕様が確定したら:

1. 該当する仕様文書に要件を追記する
2. 設計判断が必要なら `docs/開発・保守ガイド.md` または専用文書を更新する
3. `docs/README.md` の索引が必要なら追記する
4. `docs/ToDo.md` にタスクがあれば更新する

### 5. Issue への決定事項追記

確定した仕様を Issue にコメントとして残す:

```
gh issue comment <number> --body "## 決定事項

- ...
- ...

## 実装方針

- ...

## タスク分割

- [ ] ...
- [ ] ..."
```

### 6. 完了判定

以下がすべて満たされていれば完了:

- [ ] 要件が docs/ の該当文書に記載されている
- [ ] 設計判断（あれば）が文書化されている
- [ ] Issue に決定事項コメントが残っている
- [ ] ユーザーが「実装に進めてよい」と判断できる状態

## 使い方

```
Issue #42 のissue整理をして
```

```
#42 をissue整理で詰めたい
```

整理が終わったら、`issue解決` スキルで実装に進む:
```
#42 のissue解決で進めて
```
