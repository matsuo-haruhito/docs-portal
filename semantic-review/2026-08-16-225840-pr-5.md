# 共通Filter/List Footerと管理UIの仕上げ

この差分は、13の一覧画面を`FilterToolbarComponent`と`ListFooterComponent`へ寄せ、RTP/rfk、外部連携フォーム、Dashboard/Login、スクリーンショット自動発見をまとめて整えています。filter値、CSV scope、return context、maintenance gateは呼び出し側に残す設計で、主要request specでも実データscopeを継続確認しています。一方、bare `button`のAction Blue指定を外した影響が既存のclassなし操作へ波及し、API仕様のbuild再実行がブラウザ標準表示へ退行します。

Watch for: **confirmed** — API仕様のbuild再実行ボタンが共通Action Blueから外れます。**confirmed** — ListFooterのpage jump/custom page param/anchorは実装されていますが、フォーム送信契約の直接テストがありません。**confirmed** — query付きmember URL正規化はTS/CJS双方に入りましたが、この分岐を固定するテストがありません。

**Verdict**: NEEDS_CHANGES

## High-level view

FilterToolbarはURL、hidden field、selected値、filter生成を画面側に残し、Componentは幅と配置だけを担当します。ListFooterも画面固有pagination hashとparamsを受け取るため、Webhook、監査ログ、既読確認、送付履歴のfilter・CSV scopeはrequest spec上維持されています。

RTPは主要一覧でstable table key、column metadata、column key、scroll wrapper、captionを維持し、rfkは検索・enum・remote selectへ適用されています。文書権限の固定tabpanel IDとWebhook詳細のreturn contextも保持されています。

Webhook/Git/外部フォルダ/Microsoft Graphフォームは、secretを再表示しない契約とremote project selected restoreを維持しています。外部フォルダの`return_to`と各integrationのmaintenance gateも維持され、対象maintenance specは成功しています。

Orangeはheader/brand mark/sidebar active railに限定され、主要操作はBlue、warning/dangerはsemantic colorのままです。ただしglobal bare-button stylingの削除は`.button`を持たない既存操作にも効き、API仕様画面に1件の視覚回帰を作っています。

member URLは`new URL(href, BASE_URL).pathname`でqueryを除去してshow/edit URLを組み立てます。実装は意図どおりですが、screenshot auditはこの分岐を直接検証していません。

## bare button境界がAPI仕様の主要操作だけを取り残す

`application.css`と`bootstrap_overrides.css`は共通primary buttonの対象を`.button`だけへ狭めています。しかしfailed/stale時の「API仕様ページの build を再実行」は`button_to`へclassを渡していません。Railsが生成するclassなし`<button>`は今回削除されたselectorに一致しなくなるため、この主要操作だけpadding、Blue background、focus ringを失います。`spec/requests/admin_api_specifications_spec.rb:202-220`は文言とPOST結果だけを確認し、class/style契約を検出しません。

## ListFooterのlink契約は守られるがjump formは未固定

ListFooterのlink pathは受け取ったparamsから対象page paramだけを除き、pageを再付与します。監査ログのfilter/CSV latest-vs-current-page、Webhookのreturn context、既読確認のCSV page、送付履歴のfilter scopeは変更後request specで確認されています。保存済み画面では`:favorite_page`と`:read_later_page`を分離し、反対側のpageとactive viewを保持してanchorを付けています。

page jumpはlinkとは別に`form_with`とhidden inputsからURLを再構成します。現行specはpagination linkのqueryを確認しますが、jump formのaction、hidden field、custom page input名、fragment付きactionを固定していません。linkだけ通ってjumpだけ条件を落とす変更を検出できない状態です。

## query付きmember URL修正は回帰テストから外れている

TS/CJS両版はpathnameを抽出してからshow/edit URLを作るため、query文字列の末尾へ`/edit`を連結する不正URLを避けます。ただし実装はprivate関数内に重複し、`spec/frontend/screenshot_audit.test.ts`の11例はmanifest、secret、URL一致、route parserだけが対象です。query付きmember linkが文字列連結へ戻っても自動検出されません。

## 検証結果

Docker上の主要pagination/filter request specは53例成功し、外部フォルダ/Git/Microsoft Graph/Webhookのmaintenance specは22例成功しました。`npm run test:screenshot-audit`は11例成功、`npm run build`、TypeScript no-emit check、`node --check script/capture_screenshots.cjs`、`git diff --check main`も成功しています。host側のRSpecはPostgreSQL socket不在で起動できなかったため、稼働中のapp/db containerで同じ対象を再実行しました。
