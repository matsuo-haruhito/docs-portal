# Diagnosticsの通常アンカー化とsticky scroll補正

Phase 3の再レビューでは、SectionNavを常時表示セクションに合うnamed navigationへ戻し、現在位置だけを`aria-current="location"`で示す変更を確認しました。クリック時はadmin header分を含むcomputed sticky top、nav高、8px余白を引き、fragmentも履歴へ反映します。Diagnosticsの認可、read-only境界、triage集計、モデル詳細の情報保持、global CSS cascadeにblocking regressionはありません。Watch for: no blocking findings. **confirmed** — 同じ差分のscreenshot artifact変更だけ、現行文書がPNG / HTMLのままです。

**Verdict**: APPROVED

## High-level view

SectionNavは`nav`内の通常anchorとなり、`role="tablist"`、`role="tab"`、`aria-selected`、roving `tabindex`を出力しません。全リンクはnative Tab順に残り、初期位置とIntersectionObserverで追跡した位置だけが`aria-current="location"`になります。

クリックscrollはcomputed `top`、nav高、8pxをtarget位置から差し引きます。申告されたbrowser evidenceでは`#configuration`、current位置、target top 101px、overflowなしまで確認され、前回のsticky overlapは解消されています。

Diagnosticsは`require_admin_only!`を維持し、追加導線はGET anchorだけです。設定warning/error、欠落ファイル、3系統の継続失敗候補は既存データから導出され、個別件数を残したまま要対応合計へ集約されます。

モデル詳細はnative Disclosure内のserver-rendered DOMに残り、件数・全体最終更新・Model Browser導線は常時表示されます。Global CSSも`.app-header` / `.app-main` / `.admin-main` scope、Bootstrap overrideのimport順、Sidebar toggle・Column Settings・navigation itemの例外を維持しています。

MHTMLへのartifact変更はDiagnostics runtimeやScreen Guide生成を壊しませんが、仕様とセットアップ文書のPNG / HTML記述が追従していません。

## SectionNavのnavigation semanticsと現在位置

前回blockingだったtab semanticsは解消されています。componentは用途別`aria-label`を持つ`nav`とfragment anchorだけを出力し、`activateTab`もclassと`aria-current="location"`だけを切り替えます。全リンクが通常のTab順に残るDOM契約とクライアント更新が一致します。

Component specはnamed navigation、fragment href、`aria-controls`、初期`aria-current`、tab role不在を固定しています。ユーザー指示どおりPhase 3構造全体の新規specは追加されていませんが、これは前回のnon-blocking提案であり、blocking gapではありません。

## admin sticky headerを含むfragment scroll

`scrollToSection`は次frameでnav高とcomputed `top`を取得し、両方と8px余白を引きます。adminの45pxをcontrollerへ複製せず、public documentでもそのsurfaceのcomputed topを使います。hashが変わる場合だけ`pushState`するため、URLは対象sectionを表し、同じlinkの反復操作で履歴を増やしません。

申告されたbrowser確認はrole/tabindex不在、click後hash、current、target位置、overflowを含みます。前回blockingだった見出し重なりはコードと実動作の両方で解消されています。

## Diagnosticsのadmin-only read-only境界

`Admin::DiagnosticsController`は`before_action :require_admin_only!`を適用します。`company_master_admin`はDashboardで専用landingへ分岐し、Diagnosticsへの直接アクセスもadmin-only gateを通れません。

変更viewにPOST/PATCH/PUT/DELETE form、retry、resend、sync、cleanupは追加されていません。Diagnostics内fragmentと既存のread-only確認先だけなので、`READ_ONLY_MAINTENANCE`中にも確認導線を維持する仕様と一致します。

## triage countとDisclosureでの情報保持

要対応合計は設定warning/error check数、DocumentFile欠落数、生成ファイル・外部送付・外部folder同期の継続失敗候補数の和です。内訳は別々に表示され、severityも項目名・数値を常時併記するため色だけに依存しません。

モデル概要はDisclosure外、詳細cardはDisclosure内のserver-rendered DOMに残ります。設定filter、failure identity/error preview、digest、Storage内訳もDiagnostics側に保持され、初回展開requestや状態変更は導入されません。
