# 監査ログ一覧のbounded paginationと共通一覧UI統合

監査ログ一覧は、絞り込み後の件数を10,000件で打ち切ってページ範囲を算出し、FilterToolbarComponentとListFooterComponentへ移行しています。主CSVの最新200件、表示中ページCSVの最大50件、metadata JSONのscope、およびRTPのtable／column keyは維持されています。ただし、固定上限内だが実際の最終ページを超えるpageを受けると、取得結果とListFooterのページ情報が矛盾します。

Watch for: **confirmed** — `page=200`のように固定上限内だが絞り込み結果の`total_pages`を超える値で、0件表示のまま「200ページ目／全5ページ相当」という不整合なページャーになります。

**Verdict**: NEEDS_CHANGES

## High-level view

検索UIは頻出条件と高度条件を用途別の幅へ整理し、既存のAI context有効化規則、invalid date保持、remote selected restore、入力長・候補数上限を引き継いでいます。exportは主CSVだけが現在ページを引き継がず、補助scopeは閉じたDisclosureに残る構成です。

一覧はbounded countから50件単位の`total_pages`を作りますが、`@page`は1〜200なら無条件に受理されるため、実件数から算出した`total_pages`との整合性が保証されていません。

## 件数ベースページャーと200ページ境界の不整合

**confirmed** — `page_param`は1〜200をすべて有効として返し、その値でoffsetを決めた後、別途bounded countから`total_pages`を算出しています（`app/controllers/admin/access_logs_controller.rb:49-52`, `app/controllers/admin/access_logs_controller.rb:110-119`, `app/controllers/admin/access_logs_controller.rb:376-379`）。例えば205件で`page=200`を指定すると、取得offsetは9,950なので一覧は0件、pagination metadataは`page: 200, total_pages: 5, total_count: 205, from: 0, to: 0`になります。

ListFooterは全5ページの番号だけを描画して現在ページを示せず、前リンクには「199ページ目へ戻る（5ページ中）」を生成します。件数表示は205件のままなので、空の一覧とも矛盾します（`app/views/admin/access_logs/index.html.slim:19`, `app/views/admin/access_logs/index.html.slim:166`, `app/views/admin/access_logs/index.html.slim:244`）。bounded countを得た直後に、要求pageが算出済み`total_pages`を超えていれば1へ戻してから一覧を取得すれば、不正pageを1へ戻す契約とListFooterの前提を揃えられます。

変更されたspecは50件境界、2ページ目、filter保持、`page=0`、200超の`page=999999`を検証していますが、1〜200内で実際の最終ページを超える値を扱っていません。報告済みの107 examples成功ではこの境界を検出できないため、`spec/requests/admin_access_logs_pagination_spec.rb`の既存ケースへ追加が必要です。

</details>
