# UI基盤polishとserver-rendered navigation再編

この差分は、検索UIを`FilterToolbarComponent`へ集約し、文書権限と保存済みの表示切替を通常のGET navigationへ戻し、生成ファイル運用画面をRTP・StatusBadge・共通design tokenへ載せ替えています。route/controllerの識別子と認可は維持され、生成ファイル操作は`public_id` + admin-only、案件公開導線は`code` + resource access checkのままです。一方、共通CSSとFilterToolbarの責務境界に、複数画面へ波及するブロッキングな回帰があります。ユーザー確認済みの`document_bookmarks_favorite`検索欄のはみ出し・ボタン重なりは重複指摘していません。

Watch for: **High / confirmed** — global table/sticky CSSが非RTP tableとRTP固定列へ横断適用されます。**Medium / confirmed** — FilterToolbarのdetails/actions順序と二重flex所有により検索actionの配置契約を満たしません。**Medium / confirmed** — bare button stylingの削除でclassなしの既存操作が無装飾になります。**Low / confirmed** — 表示中一括選択のブラウザ挙動は未テストです。

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed:** RTPの`table_key`、column key、caption、focus可能scroll wrapperは維持されていますが、追加された`thead th`、`tbody tr:hover > td`、`.table-scroll:has(...)`はRTP rootへscopeされていません。保存済み列幅・固定列をgemに任せる境界と、非RTP tableを巻き込まない境界の両方を外れています。

**Confirmed:** FilterToolbarは業務parameterとrfk fieldを呼び出し側へ残す一方、DOM順がfields → full-width details → actionsで、仕様の「検索buttonは最後の入力直後」と一致しません。6つのadmin一覧では外側formとComponent bodyの両方が旧flex classを所有し、生成ファイル2一覧は更新仕様に反して専用filter shellを新設しています。

文書権限と保存済みはactive sectionだけをSSRし、`nav`内のGET linkのactive項目だけへ`aria-current="page"`を付けています。旧tab role、`aria-controls`、roving tabindex、Stimulus registration、controller本体、テスト、inventory参照は一括削除され、残存参照はありません。

StatusBadgeのtoneは診断のsuccess/warning/error、生成イベントのdraft/running/completed/failed、生成runのrunning/completed/failed/inactiveへ明示変換されています。rfk fieldのselected value、RTP metadata、tree_view integrationには変更がなく、route/controller側ではadmin `public_id`、public project `code`、admin-only gate、maintenance拒否、safe `return_to`が維持されています。

**Confirmed:** button stylingを`.button`へ狭めた一方、既存のclassなしsubmit/mutationを同時移行し切れていません。少なくとも品質チェックの絞り込みとAPI仕様build再実行が、操作の重要度を示すproduct stylingを失います。

## Global table stylingがRTPと非RTPの境界を越える

**High / confirmed.** `app/frontend/entrypoints/application.css:365-373`はbare `thead th`と`tbody tr:hover > td`へproduct colorを付け、同ファイル`1848-1858`は11行以上あるすべての`.table-scroll`を高さ制限付きscroll containerにして全header cellを`z-index: 3`のstickyへ変えます。`docs/specs/閲覧画面とUI.md:16,106-109`は`.data-table`またはRTP rootへのscope、RTP固定列へのglobal sticky禁止、非RTP bulk tableは専用selectorに限定することを同じ差分で正本化しており、実装が正本と逆です。

`.table-scroll`は公開案件一覧の非RTP table、bulk editの専用scroll table、閲覧可能文書・定期ジョブ・文書権限・文書マスタ等のRTP tableで共有されています。RTP側はpinned columnを持つため、全`th`への同一sticky/z-index指定が、gem管理の固定列とheader交点のstackingを画面側から再定義します。header/hover/sticky selectorをRTP table rootと明示的な`.data-table`へ限定し、bulk editは`.bulk-edit-selection__table` scopeだけに残す必要があります。

## FilterToolbarのDOM順とflex所有がaction配置を崩す

**Medium / confirmed.** `app/components/filter_toolbar_component.html.slim:2-14`はfieldsの後にdetails、その後にactionsを描画し、`app/frontend/entrypoints/admin_layout.css:285-288`はdetailsへ`flex: 1 0 100%`を与えています。detailsが1行を占有してからactionsが続くため、文書一覧・文書マスタ・監査ログの検索buttonは最後の常時表示field直後ではなくdetailsの後段へ送られます。更新仕様`docs/specs/閲覧画面とUI.md:86-89`の「検索buttonは最後の入力直後」と一致しません。

会社、ユーザー、案件、案件所属、文書マスタ、文書権限の6画面は、外側formへ`admin-filter-toolbar__form`を付け、その内側でComponent bodyにも同じclassを出力します。`admin_layout.css:251-258`がこのclassをflex container化するため、formとComponent bodyが二重にtoolbar layoutを所有します。Componentを唯一のshell/layout ownerにし、actionsを常時表示fieldsと同じrowへ置いた後でdetailsを描画し、外側formから旧layout classを外す必要があります。

## 生成ファイルfilterは新しい共通化仕様と乖離する

**Medium / confirmed.** `docs/specs/閲覧画面とUI.md:190-193`は生成ファイルイベント・実行履歴を「共通FilterToolbar」で描画すると定めていますが、`app/views/admin/generated_file_events/index.html.slim:56`と`app/views/admin/generated_file_runs/index.html.slim:58`は専用の`card generated-file-filter` shellと専用grid/action CSSを新設しています。field parameterとbulk retry contractは維持されていますが、filter shell・actions・accessibility namingの責務が共通Componentと画面専用実装へ二重化しています。

複雑な7-field gridを共通Componentが扱わない設計なら、正本から「共通FilterToolbar」を外して例外境界を明記する必要があります。共通化対象なら、Componentへdetails/grid slotを渡して専用shellの重複を削除する必要があります。

## `.button`必須化で既存の重要操作が無装飾になる

**Medium / confirmed.** `app/frontend/entrypoints/application.css:438`と`bootstrap_overrides.css:29-94`はbutton stylingをbare `button`から`button.button`へ狭めましたが、`app/views/document_version_quality_checks/show.html.slim:78`の「絞り込む」と`app/views/admin/api_specifications/show.html.slim:119`の「API仕様ページの build を再実行」はclassなしのbuttonを生成します。前者は検索Primary、後者はmutation Primaryであり、この差分後はborder/background/focus/disabledを含む共通button contractを受けません。

scope縮小を戻さず、classなしbutton/button_toを横断確認して`.button`とsemantic variantを付与する必要があります。更新仕様もsubmitを含む操作要素への`.button`明示を要求しているため、CSS変更と呼び出し側移行を同時に完了させるべきです。

## 表示中一括選択はmarkupだけがテストされる

**Low / confirmed.** `bulk_edit_selection_controller.js:48-88`は`row.hidden`を境界に表示中checkboxだけを選択・解除する新しい状態変更を追加していますが、変更されたrequest specはボタン文言とcontroller markerの存在だけを確認しています。検索中、`選択済みだけ表示`中、disabled checkbox、非表示row維持、選択/表示件数、submit enabled状態の更新はブラウザ挙動として実行されません。

Stimulus/DOM behavior specで、少なくとも検索で非表示のrowが変化しないこと、解除後に件数とsubmit状態が再計算されることを固定する必要があります。

## 検証結果

Docker app service上で変更対象のRSpec 169件、Vite production build、`git diff --check`は成功しました。host側RSpecはDB hostname `db`を解決できずload前に停止したため、同じ対象を稼働中のDocker app/dbで再実行しました。PNGはユーザー提示済みのbookmark検索欄問題を既知事項として除外し、このpassでは新しいvisual evidenceを取得していません。
