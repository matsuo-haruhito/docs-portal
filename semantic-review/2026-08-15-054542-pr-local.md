## High-level view

RTP tableのheader/hover styleは`.data-table`またはRTP table rootへscopeされ、長表stickyはRTPを直接子に持つ`.table-scroll`だけへ限定されました。gemが使うpinned/fixedのclass・data属性4種をすべて除外しているため、固定列の`position`、`left`、`z-index`はgem所有のままです。非RTPのBulk Edit stickyも専用selectorへ分離されています。

FilterToolbarはComponentがbody、fields、actions、details、active filterのlayoutを所有し、外側formはcallerに残っています。actionsはfields collectionの末尾、detailsより前に描画されるため、検索Primaryと条件クリアSecondaryは最後の常時表示入力の直後にまとまります。生成ファイルevent/runも共通Componentを使い、従来の全filterを保持しています。

button stylingは`.button`へscopeされたまま、変更差分内のsubmit・mutationへclassが明示されました。文書権限と保存済みはGET navigation + active linkの`aria-current="page"`を維持し、inactive section、tab role、`aria-controls`、client-side tab controllerを戻していません。

route/controller/internal key、認可、maintenance-mode、safe `return_to`、StatusBadge tone、rfk selected value、RTP `table_key` / column key、tree_view、生成ファイル診断値のredaction境界に変更は見つかりませんでした。生成ファイルの再投入・再実行は既存admin routeと`public_id`を使い、対象件数・最大100件・filter scopeを維持しています。

## RTP stickyは固定列の所有権をgemへ残す

前回の**High / confirmed**は解消済みです。`app/frontend/entrypoints/application.css`のheaderとhoverは`:is(.data-table, table[data-rails-table-preferences-table-key-value])`へscopeされ、長表の高さ制限とstickyはRTP tableを直接含むwrapperかつ11行以上に限定されました。非RTP tableへ波及するbare `thead` / `tbody` selectorはありません。

`position: sticky`と`z-index: 1`は、`.rails-table-preferences-pinned`、`.rails-table-preferences-fixed`、`data-rails-table-preferences-pinned="true"`、`data-rails-table-preferences-fixed="true"`の全markerを持たないheaderだけに適用されます。gem CSSは同じ4 markerに`position: sticky`、CSS variable由来の`left`、body `z-index: 2`、header `z-index: 3`を定義しており、host側selectorは上書きしません。Bulk Edit tableは`.bulk-edit-selection__table thead th`だけがstickyです。

## FilterToolbarはshellだけを所有し業務契約をcallerへ残す

前回の**Medium / confirmed** 2件は解消済みです。`FilterToolbarComponent`はfield wrapper、toolbar body、actions、details、active filter listだけを生成し、GET form、URL、hidden `view`、filter parameter、rfk helper、表示条件、認可判定は各Slimに残っています。外側の`.filter-toolbar__form`は`min-width: 0`だけを持つため、以前の二重flex所有はありません。

actionsは`.filter-toolbar__fields`内でfield群の直後、detailsはtoolbar bodyの後です。Primary検索とSecondary clear/exportは常時表示fieldと同じflowにあり、詳細条件Disclosureの後へ回りません。生成ファイルevent一覧は`q`、`status`、`operation`、`event_source`、`path`、`scheduled_from`、`scheduled_to`、run一覧は`q`、`status`、`job_id`、`generator`、`output_writer`、`event_source`、`created_from`、`created_to`をslotへ渡しています。

## classなしbuttonとnavigation/status境界

前回の**Medium / confirmed**は解消済みです。bare buttonのPrimary overrideは復活させず、今回変更されたsubmit/actionへ`.button`とvariantが明示されています。追加行にclassなしの`button_to`、`button_tag`、`form.submit`、`submit_tag`はありません。

文書権限と保存済みはactive linkだけに`aria-current="page"`を付けるGET navigationで、active sectionだけがSSRされます。StatusBadgeは診断、文書利用状況、生成event/runで明示的なtone mappingと日本語labelを使っています。

## Bulk Editの表示中一括操作は実行テストがない

**Low / confirmed.** `bulk_edit_selection_controller.js`はhiddenでないrowだけのcheckboxを変更し、disabled checkboxを除外して`refresh()`で件数とsubmit状態を再計算します。しかし変更されたrequest specはボタンとcontroller markerの存在だけを確認し、このDOM挙動を実行していません。

検索で非表示になったrowの保持、`選択済みだけ表示`中の解除、disabled row、0件へ戻したときのsubmit disabledをStimulus/DOM testで固定すると、このgapを閉じられます。
